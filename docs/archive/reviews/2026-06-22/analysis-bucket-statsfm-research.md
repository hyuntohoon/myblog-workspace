## 1. 현재 상태 감사 (코드/문서로 검증)

### 1.1 "분석 버킷"의 정체 — 이름이 오해를 부른다

가장 먼저 바로잡을 사실: **"분석 버킷"은 DB의 버킷(`review_buckets`) 엔티티가 아니다.** `/profile` 대시보드의 5개 탭(개요·평론·평론 버킷·**분석 버킷**·연동) 중 하나이며, 내부 id는 `stats`, 컴포넌트는 `StatsTab` → 그냥 `LikedBoard`로 패스스루된다(`myblog_front/src/components/member/ProfileApp.tsx:17-23`, `StatsTab.tsx:12`). 즉 **분석 버킷 = "좋아요한 트랙 워크벤치"(`LikedBoard`) + 내장 분석 패널(`LikedAnalysis`)** 이다.

"버킷"이라는 단어가 두 축에서 충돌한다 — 혼동 주의:

- **탭으로서의 버킷**: 분석 버킷 / 평론 버킷 (UI 탭)
- **DB 엔티티 `review_buckets.kind`**: `'review'` | `'spotify_library'` — 이건 *평론 버킷* 탭 소관이지 분석 버킷과 무관.

분석 버킷은 탭이고 `kind`가 없다. 이름이 "버킷"이라 마치 독립 객체처럼 읽히지만 실제론 `spotify_saved_tracks` 캐시 + `/profile` 섹션이다. (출처: `FEAT-genre-artist-distribution.md` Non-goals가 "track-grain review_bucket 아님"이라고 직접 명시.)

기원: `FEAT-genre-artist-distribution`(PR #182, 평면 분포 패널) → `FEAT-liked-tracks-workbench`(PR #187/#192, 트랙 워크벤치로 재설계). Step 5(unlike)는 DROP.

### 1.2 분석 버킷이 지금 보여주는 것

- **좋아요 트랙 테이블** — 전량 적재(offset 페이지네이션 `PAGE=500`, **`CEILING=1000`**). 좋아요가 1000개를 넘으면 테이블엔 안 실린다.
- **분석 패널 4종**:
  - 장르 분포 / 아티스트 분포(top-8) → **서버 집계**(전량 정확)
  - 좋아요 흐름(주간) / 연대 분포 → **클라이언트 집계**(적재된 ≤1000행에서만 계산)
- **좋아요/재생 소스 토글**: 같은 장르·아티스트 차트를 saved-tracks(좋아요) ↔ play-history(재생) 두 소스로 전환.
- **차트 스타일 토글**: 막대/도넛/트리맵/태그/리스트.
- **미분류 → 분류하기 버튼**: catalog-sync(classify) + 장르 채우기(fill-genres) 두 enqueue를 동시 발사(둘 다 202, 워커/로컬 폴러가 실제 작업 — hard rule #9).
- **테이블 상호작용**: 검색, 장르/아티스트 패싯, 정렬, 그룹핑, 행 메뉴(작품 상세 / 평론 버킷에 담기 / 평론 쓰기).

### 1.3 데이터 소스와 핵심 사실 — 재생 이벤트 시계열은 *있다*

이 과제의 전제("좋아요한 트랙이라는 집합만 있다")는 **코드상 거짓**이다. 시스템은 재생 이벤트 시계열을 실제로 적재·보존한다:

| 테이블 | 성격 | 입력 | 한계 |
|---|---|---|---|
| `spotify_saved_tracks` (V24/26) | 좋아요 **집합**, `added_at` 보유 | 일일 증분 + 주간 full | 증분은 unlike 안 지움(최대 ~7일 stale) |
| `spotify_play_events` (V10) | **앨범 단위** 영구 append-only 재생 로그, `played_at`만 | 시간당 cron × 최근재생 50개 창 | 시간당 50건 초과 시 영구 유실, 트랙 정보 없음 |
| `spotify_track_play_events` (V19) | **트랙 단위** 영구 로그 | 동일 | **앱에서 읽는 리더가 아직 없음** (이미 만들어 둔 잠재 자산) |
| `spotify_recent_albums/tracks`, `now_playing` | 회전 캐시(영구 아님) | 매 tick prune | 스냅샷 |

집계는 전부 요청 시점 즉석 계산(`myblog_backend/app/services/distribution.py` `rank_counts` 한 함수, top-N 캡 없음). 롤업 테이블 없음. 동기 Spotify 호출 없음(hard rule #9 준수 — 표시 숫자는 100% DB 파생). 읽기 엔드포인트는 모두 `myblog_backend/app/api/routes/library.py`(myblog_music 아님).

엔드포인트: `GET /api/library/saved-tracks/{genre,artist}-distribution`, `GET /api/library/play-events/{genre,artist}-distribution`, `GET /api/library/saved-tracks`, `POST /api/library/saved-tracks/classify`, `POST /api/library/saved-tracks/fill-genres`.

### 1.4 지금 잘 하는 것 (Q1)

1. **아키텍처 방향이 옳다**: "의미 있는 분석은 동기 API 호출이 아니라 *소유·축적한 데이터*에서 나온다" — 이건 Stats.fm가 비싸게 증명한 원리인데, 이 프로젝트는 이미 그 구조(워커가 play_events를 축적)를 갖고 있다.
2. **미분류를 정직하게 노출**: 장르 분포에서 null을 조용히 버리지 않고 `unclassified_count` + uncatalogued/ungenred breakdown으로 표면화(`library_service.py:325-343`). 데이터 품질을 숨기지 않는 드문 미덕.
3. **깔때기로서의 통합**: 행 메뉴 "평론 버킷에 담기"가 평론 버킷 API를 재사용 — 탐색 → 분류 → 담기 → 쓰기의 인테이크 동선.
4. **소스-불가지 차트 계약**: 좋아요/재생을 같은 응답 형태로 렌더 → 코드 단순.
5. **비용/경계 규율**: $0 바이어스, 단일 사용자, 동기 Spotify 금지 — 일관되게 지켜짐.

### 1.5 지금 설명·측정·탐색하지 못하는 것 (Q2)

- **청취 시간(분/시간)을 절대 못 보여준다.** 모든 재생 테이블이 `played_at`만 저장, `ms_played`/종료시각/스킵 플래그 없음. `duration_ms`는 트랙의 *전체 길이*지 실제 청취 시간이 아니다. → "내가 가장 오래 산 앨범" 같은 핵심 비평 근거가 구조적으로 불가능.
- **헤드라인 분석이 지금 대부분 노이즈**: 프로덕션 실측 — 좋아요 1,017곡 중 **71%가 uncatalogued**(재생은 4%). 분석 버킷의 기본 뷰(좋아요 장르 분포)는 현재 대부분 미분류로 채워진다. "분석"을 표방하지만 가장 신뢰 가능한 신호 위에 서 있지 않다.
- **트랙 단위 청취를 못 본다**: `play_events`가 앨범 단위 → 한 곡 스킵과 앨범 통청이 똑같이 "재생 1". (트랙 단위 V19 로그는 있는데 리더가 없음.)
- **진짜 누적/장기 추세 불가**: 시계열 지평이 "첫 배포일 이후"로 묶이고, 시간당 50창 때문에 헤비 세션은 과소집계. 백필 경로 없음.
- **두 소스가 똑같이 생긴 차트 뒤에 숨음**: 좋아요(집합/의도)와 재생(행동)을 작은 토글 하나로 전환 — 사용자가 무엇을 보는지 오독하기 쉽다.
- **분모 불일치**: 좋아요 흐름/연대(≤1000 클라이언트)와 장르/아티스트(전량 서버)가 다른 모집단을 쓴다.
- **쓰기 연결이 약함**: 행 "평론 쓰기 →"는 앨범 컨텍스트 없는 **맨 `/write`** 링크(`LikedBoard.tsx:188-194`). 진짜 컨텍스트 동선은 작품 상세 → `/write?album=`뿐. 리서치 노트·편집/비평 플로우와는 직접 연결 0.

### 1.6 제품 방향 (문서로 검증한 가장 load-bearing한 사실)

이건 1인 음악 **비평·집필** 시스템이지 소셜/스트리밍-분석 제품이 아니다. 포지셔닝 문서가 척추를 "Letterboxd 기반, IZM 표면"으로 규정 — 권위는 **목소리 + 큐레이션**에서 나오지 크라우드 집계에서 나오지 않는다. 분석 표면은 *집필 깔때기를 먹이는 비공개 워크벤치 도구*이지 독자용 청취 분석이 아니다(분석 버킷은 `/profile` 가드 뒤, 좋아요 집합은 절대 공개 안 함).

여러 RFC가 명시적으로 거부: ML/자동추천 없음(`FEAT-review-bucket-board`, `FEAT-genre-artist-distribution`), per-track 장르 분류기 없음(Spotify가 2024-11 track/artist 장르 폐기), 라이브 차트/리더보드/실시간 집계 없음(market research NOT-adopt #6), 점수 리더보드 없음. `FEAT-genre-recommendation`은 **FROZEN**(평론 ~1편으론 랭크할 게 없음). `docs/plan.md` Active는 **비어 있음**.

### 1.7 추가 발견 (인접 부채)

- **죽은 컬럼**: `Track/Artist/Album.views` 어디서도 안 써짐 → `top-tracks` `ORDER BY views DESC`가 무효(popularity/release_date로 폴백).
- **아티스트 귀속 미모델링**: `album_artists.role` / `track_artists.role` 항상 NULL. 협업 앨범이 콤마-결합 "A, B" 단일 라벨로 집계 → 단독 "A" 카운트를 파편화. 1차/피처 구분 없음.
- **장르 staleness**: `artists.genres`는 첫 photo-enrich에서만 기록(`sync_service.py:232` `photo_url` 비었을 때만) → 재싱크 시 미갱신. + Spotify 장르 폐기 → post-2024 앨범 다수 미분류.
- **genres/tree 중복 카운트**: 멀티장르 앨범이 장르마다 1회씩 카운트 → 막대 합이 앨범 총수와 불일치.
- **버킷 명명 드리프트**: 한 객체에 4개 어휘(평론 버킷/크레이트/`review_buckets`/`crMeta`). `FEAT-bucket-identity` Direction A만 DONE, B/C/D 미착수.
- **문서 staleness**: `docs/architecture.md`는 분석 버킷/saved-tracks/distribution 표면을 전혀 안 다룸(자체 drift 배너). `docs/rfcs/README.md`는 `FEAT-genre-artist-distribution`을 아직 "draft/미착수"로 표기(실제 DONE+prod-live 2026-06-21).

## 2. Stats.fm 리서치 요약

### 2.1 핵심 메커니즘 (확정 사실)

Stats.fm의 진짜 핵심 가치는 **개인 청취 분석**이며, 데이터가 **두 층**으로 갈린다:

- **(A) Spotify API only (기본/무료)**: top tracks/artists를 Spotify의 불투명 *affinity* ML로 랭크. **고정 3개 구간만**(short ~4주 / medium ~6개월 / long **~1년**, all-time 아님), 최대 ~99개, **재생수 없음**. Stats.fm 스스로 "꽤 부정확"이라고 인정.
- **(B) Extended Streaming History 임포트(GDPR 내보내기)**: 여기서 진짜 깊이가 나온다 — 실제 재생수, 전체 평생 히스토리, 재생수/청취시간 정렬, 커스텀 구간. **이 임포트는 Stats.fm Plus(유료)** 필요.

핵심: **분석적 깊이는 라이브 API가 아니라 소유·임포트한 히스토리에서 나온다.** Spotify API는 어떤 엔드포인트로도 청취 분(minutes)이나 절대 재생수를 주지 않는다 — `ms_played`는 오직 GDPR Extended export(스트림당 1행)에만 존재.

### 2.2 확정된 기술 제약 (공식 문서 대조 완료)

- `GET /me/player/recently-played`: 요청당 **최대 50**, before/after 커서, `played_at` 제공, 집계 없음, 팟캐스트 제외. **깊은 과거 페이징 불가**(문서 명시 아님 — 실측 동작). → 폴러가 멈춘 구간은 **영구 유실**, 시작 전 과거는 복원 불가.
- `GET /me/top/{type}`: `artists`|`tracks`만(**top-albums 없음**), affinity 랭크, 재생수/분 없음, 3개 고정 구간(`long_term` = ~1년, all-time 아님).
- **dev mode = 5 사용자**(2026-02 이전엔 25 — 정정됨), 소유자 Premium 필수, Client ID 1개. Extended quota는 조직 전용(250k MAU 최소) → 개인은 사실상 불가. **Refresh token 6개월 수명** → 헤드리스라도 연 2회 수동 재인증 필요.
- **Spotify Developer Policy가 "파생 청취 지표/사용 통계/유저 메트릭 생성"을 금지.** → 스트리밍-통계 대시보드는 엄밀히 비준수. 비공개 1인 도구는 단속 risk 낮지만 **공개/공유 stats 제품으로 내보낼 수 없고**, Spotify 콘텐츠 표시 시 Spotify Marks 귀속 필수.
- Extended export: 평생, JSON(.zip), 배달 ~최대 30일. 스트림당 필드 = `ts`, `ms_played`, `skipped`, `offline`, `reason_start/end`, `shuffle`, 트랙/아티스트/앨범 + URI. Stats.fm는 표시 시 스킵/<30초/로컬/팟캐스트를 필터 → 표시 재생수 ≠ 원본 행수.

### 2.3 중심 기능 vs 사회적 기능

- **중심(분석 가치)**: top 트랙/아티스트/앨범/장르, 청취 시간, 재생수, 시간 구간/커스텀, listening clock, 항목별 드릴다운, 전체 히스토리 탐색.
- **사회적/장식/참여(핵심 아님)**: 친구, 소울메이트/궁합, Top Listeners/리더보드(공개 경쟁), 공유 프로필, Wrapped식 공유 카드. 이들은 *남과 비교/방송*이지 내 취향 분석이 아니다.

### 2.4 합리적 추론(확정 아님)

- Stats.fm의 진짜 차별점은 Wrapped 대비 *상시·평생·드릴다운* — 단 임포트 후에만. 무료 API 뷰(불투명 top 리스트)와 임포트 뷰(정확한 카운트)를 혼동하면 안 됨.
- 분석적 깊이는 사실상 유료화되어 있음(임포트·고급 차트·Apple Music·총 청취분이 Plus 뒤).
- Plus 가격/일회성-vs-구독은 지역·플랫폼 의존(공식 페이지엔 가격 없음). App Store의 가격대/Pro SKU/iOS 버전은 마케팅 메타데이터로 미검증 처리.

## 3. 이전 가능한 원칙 (복제가 아니라 차용) (Q3, Q5)

각 원칙은 "왜 이 제품에 구조적으로 유용한가"로 정당화한다.

1. **소유 데이터 = 분석의 토대.** Stats.fm가 증명: 의미 있는 분석은 라이브 API가 아니라 축적/임포트한 데이터에서 나온다. → 이 프로젝트가 이미 옳은 방향. 강화하되 동기 호출로 후퇴하지 말 것.
2. **재생수 ≠ 청취 시간은 별개 축이고, 둘 다 명시해야 한다.** Stats.fm는 Count/Time-played를 분리하고 "time-played는 긴 곡에 유리"라고 경고. → 지금 이 시스템은 *카운트만* 가능하므로, "재생 시간"이라는 단어를 UI에서 쓰면 거짓말이 된다. 용어를 "재생 *횟수*"로 못박는 게 원칙.
3. **항목별 드릴다운이 1인 비평의 진짜 가치.** "이 앨범을 얼마나/언제/무엇과 함께 들었나"는 평론에 인용할 *증거*가 된다. Stats.fm의 소셜 절반은 버리고 이 드릴다운만 차용.
4. **데이터 출처/모집단을 화면에 정직히 표기.** Stats.fm는 "스킵/<30초/팟캐스트 제외", "API는 부정확" 같은 한계를 문서로 공개. → 이 제품도 "좋아요(의도) vs 재생(행동)", "미분류 N%", "첫 배포일 이후"를 차트에 라벨로 박아야 오독을 막는다.
5. **GDPR Extended export = API가 못 주는 모든 것의 단일 해금 키.** 평생 재생수·청취 시간·연도/시대 회고·스킵 여부가 전부 이 파일에 있다. *Stats.fm Plus 없이도* 내가 JSON을 직접 파싱하면 동일 원재료 확보 — "소유 데이터" 모델에 완벽히 부합.
6. **소비 측정과 판단 측정의 분리.** Stats.fm는 소비(consumption)만 측정한다. 비평은 판단(judgment)을 측정한다. → 정량 청취 근거를 *별 점수/리뷰 텍스트*(편집 판단) 옆에 **나란히 두되 합치지 않는** 것이 차용할 패턴.

### A. 저비용 개선 — 기존 데이터만으로 (Q9, Q5)

이 그룹이 **임포트·인제스션 이전에 먼저 해야 할 일**이다. 지금 토대가 노이즈(71% uncatalogued)인데 그 위에 차트를 더 얹는 건 gold-plating이다.

1. **좋아요 집합의 카탈로그/장르 커버리지부터 끌어올리기.**
   - 가치: 헤드라인 분석을 노이즈→신뢰로. *모든* 후속 분석의 전제.
   - 데이터: 기존 classify/fill-genres 파이프라인(이미 존재). 신규 수집 0.
   - 리스크: 낮음. 단 `artists.genres` 갱신 버그와 Spotify 장르 폐기로 천장 존재 → iTunes/LLM 백필 의존.
   - 근거: 새 데이터 없이 가장 큰 정직성 향상.
2. **데이터 출처/모집단 라벨링(좋아요 vs 재생, 미분류 %, 시계열 지평).**
   - 가치: 오독 방지(§7의 거의 전부를 UI 한 줄로 차단).
   - 데이터: 이미 응답에 있는 `unclassified_breakdown`, `last_synced_at` 노출만.
   - 리스크: 거의 없음.
3. **"재생 시간" 용어 제거 → "재생 횟수"로 통일 + 앨범 단위 한계 명시.**
   - 가치: 측정 불가능한 지표를 약속하지 않음.
   - 데이터: 없음(문구/툴팁). 리스크: 없음.
4. **아티스트 분포의 콤마-결합 라벨 분해(피처링/협업 귀속).**
   - 가치: "A, B" 결합 버킷이 단독 "A"를 파편화하는 현상 제거.
   - 데이터: 기존 album_artists 조인(역할 NULL이라 단순 분해까지만).
   - 리스크: 낮음~중.
5. **클라이언트 위젯(좋아요 흐름/연대)의 ≤1000 모집단 명시 또는 서버 집계로 승격.**
   - 가치: 분모 불일치 제거. 데이터: 서버 집계 시 엔드포인트(소), 표기만 하면 0. 리스크: 낮음.
6. **이미 적재 중인 `spotify_track_play_events`(V19)에 리더 붙이기.**
   - 가치: "가장 많이 돌린 곡". 이미 비용 지불한 자산 활성화.
   - 데이터: 신규 수집 0, 백엔드 집계만. 리스크: 낮음(50창/시간당 과소집계 상속).

### B. 중간 규모 — 추가 수집/집계 필요 (Q6)

1. **GDPR Extended Streaming History 1회 임포트(JSON 직파싱).** ← 이 그룹의 핵심.
   - 가치: API로 *불가능한 모든 것* 해금 — 진짜 평생 재생수, **청취 시간(ms_played)**, 연도/시대별 회고, 스킵/통청 구분, "내가 진짜 끼고 산 앨범".
   - 데이터: 사용자가 Spotify에서 요청(~최대 30일 대기) → ZIP/JSON → 신규 스키마(스트림 단위 테이블) + 파서.

   - 근거: 신규 수집·스키마 필요하나 외부 비용·실시간 동기화·ML 불요. "소유 데이터" 모델 부합.
2. **앨범 단위 청취 "강도" 요약을 평론 작성 화면에 근거로 노출(자동 점수 아님).**
   - 가치: `/write?album=`에서 "재생 N회 · 첫/마지막 청취"를 *참고 정보*로. 편집 판단 보조.
   - 데이터: 기존 play_events 집계 + (임포트 시) 청취 시간.
   - 리스크: 중. **자동 추천/점수로 미끄러지지 않도록** "표시만". 행 "평론 쓰기" 맨 링크 문제도 함께 해결.
3. **시간 구간 필터(이번 달/올해/시대) — 단 임포트 데이터 위에서만.**
   - 가치: Stats.fm 커스텀 구간 차용. 회고형 글쓰기 지원.
   - 데이터: 임포트(B-1)에 의존(라이브 API는 3고정 구간뿐). 리스크: 중, B-1 선행.

## 6. 제품 권고

**정의 (1–2문장):**

> 분석 버킷은 *내가 이미 좋아요·재생한 음악 기록*을 정확하고 정직하게 읽고 탐색해, 평론 집필로 이어지는 **1인용·비공개 인테이크 워크벤치**다. 목적은 자동 추천·점수·사회적 비교가 아니라, 내 편집적 판단에 *근거(증거)* 를 제공하는 것이며 — 소비를 측정하되 판단은 측정하지 않는다.

**다음으로 가장 가치 있는 *조사* 방향 (구현 아님):**

**GDPR Extended Streaming History 임포트의 타당성 조사.** 이유: (a) 현재 데이터로 구조적으로 불가능한 모든 것(진짜 누적 재생수·청취 시간·시대별 회고·스킵 구분)을 외부 비용·실시간 동기화·ML 없이 단번에 해금하고, (b) "소유 데이터" 아키텍처에 완벽히 부합하며, (c) Stats.fm Plus의 유일한 실질 가치를 무료로 자가 복제한다.

단, **명시적 게이트**를 건다 — 임포트 조사보다 **먼저 그룹 A-1(좋아요 카탈로그/장르 커버리지)와 A-2/A-3(출처 라벨링·용어 정정)** 를 처리할 것. 지금은 토대가 71% 미분류라, 임포트해도 노이즈 위에 노이즈를 쌓을 뿐이다. 저비용 정직성 작업으로 토대를 신뢰 가능하게 만든 *뒤에* 임포트를 조사하는 순서가 옳다.

## 7. 열린 질문 (RFC 전 사용자 판단 필요)

1. **좋아요 vs 재생, 무엇이 분석 버킷의 1차 데이터인가?** 좋아요(의도/열망)와 재생(행동)은 다른 것이다. 지금은 좋아요가 기본인데 71% 미분류다. 비평 근거로는 재생이 더 솔직하지 않은가? 기본 소스를 무엇으로?
2. **GDPR 임포트를 실제로 할 의향이 있는가?** 1회성·수동·~30일 대기·반복성 낮음. 이 마찰을 감수할 만큼 "청취 시간/평생 회고"가 글쓰기에 가치 있는가, 아니면 카운트만으로 충분한가?
3. **스킵/<30초/팟캐스트 필터 정책을 어떻게 정의할 것인가?** Stats.fm 기본값을 따를지, 비평 목적에 맞게 직접 정할지(예: 스킵도 "한 번 시도했다"는 신호로 볼 수도).
4. **"재생 시간"을 정말 보여주고 싶은가?** 보여주려면 임포트 필수. 안 한다면 UI에서 시간 어휘를 전부 "횟수"로 교체해야 한다 — 어느 쪽?
5. **분석 → 글쓰기 연결을 어디까지 강화하나?** "표시만"의 경계선은? "이 앨범 N회 청취"를 작성 화면에 띄우는 것까지는 OK인가, 그조차 판단 오염인가?
6. **시계열 지평이 "첫 배포일 이후"인 점을 수용하는가?** 임포트 없이는 그 이전 평생 기록 복원 불가. 회고형 글에 치명적인가?
7. **분석 버킷과 평론 버킷을 장기적으로 합칠 것인가?**(`FEAT-bucket-identity` Direction C) — 별개 의도인가, 점진적 빌드의 우연인가? 이 미해결 질문이 분석 버킷 정보구조 결정에 선행한다.
8. **Spotify Developer Policy의 "파생 지표 금지"를 어떻게 다룰 것인가?** 비공개 1인 도구 한정(현 방향) 확정인가? 어떤 형태로도 공개/공유 계획이 없다고 못 박을 수 있는가?

## 8. 비판적 총평

- 가장 큰 약점은 기능이 아니라 **정직성 부채**다: "분석"을 표방하는 탭의 기본 뷰가 71% 미분류이고, 측정 불가능한 "재생 시간"을 연상시키며, 좋아요(집합)와 재생(행동)을 같은 차트로 흐릿하게 섞는다. 차트를 더 만들기 전에 *모집단·출처·한계를 화면에 박는* 저비용 작업이 ROI가 가장 높다.
- **오버엔지니어링 함정**: 임포트·트랙단위·시간구간은 매력적이지만, 토대(커버리지)가 노이즈인 상태에서 착수하면 정밀해 보이는 거짓을 양산한다. 순서가 전부다.
- 다행히 제품의 *방향*(소유 데이터·비추천·비소셜·$0·비공개)은 Stats.fm 리서치와 Spotify Policy가 **독립적으로 정당화**해준다. Stats.fm에서 베낄 건 거의 없고, 베끼지 말아야 할 것(소셜 절반)이 명확하며, 이미 옳게 한 것(소유 데이터)을 *더 정직하게* 다듬는 게 핵심이다.

### 9.1 live prod 진단 결과

**좋아요(saved) — 커버리지 이미 100%**
- 1,017곡 전부 카탈로그 연결(album_id NULL = 0), 816앨범 전부 장르 보유(미장르 = 0), 트랙 단위 미분류 = 0.
- "71%"는 약 하루 전 스냅샷 — 04:00 launchd + on-demand 폴러 백필이 메웠고 신규 좋아요도 self-healing. → **올릴 커버리지 없음.**
- 단, 장르 신뢰도는 균일하지 않음: low-confidence ~318앨범(itunes 138 / llm 99 / mapping 81).

**재생(played) — "favorite=최다재생" 신호는 아직 어림**
- 앨범단위 `spotify_play_events`: 854 이벤트 / 227앨범 / 기간 2026-06-03~06-21(**18일**). 1회재생 147앨범(65%), 5회+ 34앨범, 최다 128.
- 트랙단위 `spotify_track_play_events`(V19): 454 / 286트랙 / 8일 · 앱 리더 없음.
- **좋아요 ∩ 재생 = 103앨범뿐**(재생 227 중). 좋아요 816 중 18일 창에서 재생된 건 103 → 좋아요(의도)와 재생(행동)은 거의 따로 논다.

핵심 결론: 진짜 병목은 커버리지가 아니라 ① 아티스트 귀속 버그, ② 좋아요 vs 재생 오독, ③ 평생 favorite 신호 부재(18일 한계).

### 9.4 디자인/UX 패턴 — 따라할 것 / 피할 것 (follow-up)

원 리포트는 Stats.fm를 *제품·데이터·IA* 수준에서 다뤘고 *시각 디자인*은 따로 감사하지 않았다(기록 누락 → 여기서 보강). 정직한 판단: 이 제품엔 이미 강한 편집 아이덴티티("Letterboxd 기반, IZM 표면" + 자체 디자인 시스템)가 있고, 분석 버킷도 이미 차트 스타일 토글(막대/도넛/트리맵/태그/리스트)·소스 토글·패싯을 갖췄다. → **Stats.fm의 시각 스킨을 베낄 건 거의 없다.** 빌릴 가치가 있는 건 *인터랙션/IA 패턴*뿐:

**따라할 인터랙션/IA** (대부분 `FEAT-listening-history-import` 표면에 자연 흡수):
- **항목별 드릴다운** — 아티스트/앨범/곡 클릭 → 그 항목 전용 stats(재생수, 첫/마지막 청취, 그 아티스트의 top 곡, 미니 히스토리). "내가 좋아하는 X가 무엇인지"의 핵심 UX. 기존 `/artist/[id]` 허브와 결이 맞음.
- **Count ↔ Time 토글** — 같은 랭킹 리스트를 재생횟수/청취시간으로 전환(Stats.fm Count/Time-played). 짧은 곡 vs 긴 곡 편향을 사용자가 직접 봄.
- **순위 행 = rank + 라벨 + 수치 + 미니 스파크라인** — top 리스트 정보 밀도.
- **시대/연도 히스토그램** — era 분포를 막대로(이미 v1 scope).
- **"on this day" / 연도별 회고 카드 레이아웃** — 임포트 회고 뷰의 표현 틀.
- (선택) **listening clock / 시간대 히트맵** — 임포트 `ts` 시각으로 가능하나 v1 비핵심 → 회고에 곁들이는 정도.

**피할 시각/UX** (편집 아이덴티티와 충돌 — §4 거부 목록의 시각적 대응물): 소비자 앱 스킨(그라데이션·화려한 애니메이션), Wrapped식 공유 카드, 배지/게이미피케이션, 리더보드 테이블, 공개 프로필 경쟁 UI.

→ 이 패턴들은 `FEAT-listening-history-import`(드릴다운·count/time·era·회고)와 `FEAT-analysis-source-clarity`(소스 라벨·정직 표기)에 흡수되므로 **별도 디자인 RFC는 불필요.** 실제 새 UI를 만들 때 `frontend-design` 스킬로 비주얼 디렉션만 잡으면 됨.
