### 1. P1-E follow-up — `DATABASE_URL` startup validation (myblog_worker #9)

**Problem**: `myblog_worker` guarded `SPOTIFY_CLIENT_ID/SECRET` on startup but not `DATABASE_URL`. Default value was a local dev URL (`postgresql+psycopg://blog:blog@127.0.0.1:5433/blog`) — if Secrets Manager failed in prod, Lambda booted silently using the wrong DB host, failing only at query time.

**Fix**:
- Changed `DATABASE_URL` default from local dev URL to `""`
- Added `DATABASE_URL` to the missing-keys check inside `get_settings()` (alongside Spotify creds)
- Made `infra/db.py` lazy: `create_engine()` deferred to first actual use (was at module import time, which caused test collection failures when `DATABASE_URL=""`

**Tests added** (`tests/test_config.py`, 7 new):
- Secrets Manager total failure → `ValueError`
- Partial missing (DB only, or Spotify only) → `ValueError` naming the missing key
- All secrets present → success
- `SECRETS_ARN` empty (local dev) → validation skipped, boot succeeds

### 2. DEBT-5 — `AlbumOut.external_url` always null (myblog_music #11)

**Problem**: `GET /api/music/albums/{id}` always returned `external_url: null`. Root cause: `album_service.py` built `AlbumOut(...)` without reading `Album.ext_refs`. The worker had been storing the Spotify URL as `ext_refs = {"spotify_url": "https://..."}` since ARCH-1 was implemented, but the music service never read it.

**Fix** (1 line):
```python
# Before
AlbumOut(id=..., title=..., spotify_id=al.spotify_id)

# After
AlbumOut(..., external_url=(al.ext_refs or {}).get("spotify_url"))
```

**Tests added** (`tests/test_unit.py`, 3 new): URL populated, empty `ext_refs`, null `ext_refs`.

### 4. ARCH-2 — Spotify client duplication decision (ADR-0004)

**Problem**: Identical `SpotifyClient` auth logic (`_get_token`, `_headers`) exists in both `myblog_music` and `myblog_worker`. Any Spotify API credential change requires two edits.

**Decision**: Accept duplication. Do not extract to a shared package.

**Rationale**:
- The two clients have diverged in purpose: music is search-focused, worker is bulk-batch focused
- Lambda deployments are independent; a shared package would require publishing and version coordination across repos
- Auth logic is ~20 lines and historically stable

**Actions**:
- `docs/decisions/0004-spotify-client-duplication.md` created
- Cross-reference comment added to both `spotify_client.py` files pointing to each other and the ADR

### 6. Gemini alias generation — EventBridge decoupling (myblog_worker #10)

**Problem**: `generate_and_save_aliases()` ran inline in `_process_batch()` after the main DB commit. This blocked the SQS sync path with up to 20 × 10s Gemini API calls (200s worst case > 120s Lambda timeout). A Gemini slowdown or outage would cause the sync Lambda to time out and redeliver the original SQS message.

**Fix**:
- Removed alias generation call from `_process_batch()` entirely
- Added EventBridge `rate(15 minutes)` scheduled trigger to `WorkerFunction` in `template.yaml`
- `lambda_handler` now dispatches on `event.get("source") == "aws.events"` for the alias path
- Reduced `LIMIT 20 → 10` so scheduled runs complete within 120s (10 × 10s = 100s max); any remaining artists are picked up on the next run

**Before / After**:

| | Before | After |
|---|---|---|
| SQS sync invocation | Sync + Gemini calls (blocking) | Sync only (fast) |
| Alias generation | Inline, holds DB connection | Every 15 min, isolated |
| Lambda risk | Timeout if Gemini slow | SQS path unaffected |

**Tests added** (`tests/test_handler.py`, 2 new):
- EventBridge event → `generate_and_save_aliases` called once
- SQS event → `generate_and_save_aliases` not called
