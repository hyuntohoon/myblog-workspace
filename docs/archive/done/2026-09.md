# Done — 2026-09

## FIX-user-flow-state-consistency — four legs, no RFC (2026-08-30 audit → 2026-09-02)

A current-main audit recorded on 2026-08-30 (ws #967) found four independently reversible classes of
state defect on user-facing surfaces. No RFC: each leg was a separate front PR with its own rollback,
and nothing crossed a repo boundary. All four shipped.

- **Leg 1 — rating mutations must be confirmed** (front #432, merged 2026-08-31). `null` album state
  became reserved for a confirmed `204`; transport and non-success responses throw instead of reading
  as "the rating is gone". Rating events are emitted only after confirmed writes, a failed delete
  stays visible without removing the row, and rerating cancellation became retryable, sequence-safe
  and serialized across albums.
- **Leg 2 — Pocket structural writes are ordered** (front #433, deploy `33322704126`, prod smoke
  19/0, 2026-08-31). One cross-island FIFO for Pocket and BucketBoard structural writes; semantic
  move/delete projections replay from the confirmed server prefix after a failure without delaying
  the optimistic UI; a stale full-tree read can no longer overwrite newer structural intent. The
  Pocket `+N` overflow marker became an accessible handoff to the full bucket page.
- **Leg 3 — a failed read is not an empty one** (front #437 `067ca82`, deploy `33479353096`, prod
  smoke 19/0, 2026-09-01). Four defects on the two search surfaces, each one state the page was
  already computing and then dropping:
  - `/search` rendered a failed unified search as *일치하는 결과가 없습니다 — 철자를 확인하거나…*.
    The hook computed `검색 실패` and the page never read it, so a 5xx or a dead network blamed the
    reader's spelling for a request that never landed. The header dropdown branched on `total === 0`
    alone, which was worse: it showed 검색 결과 없음 for the whole round trip of *every* search.
  - `loadReviews()` resolved `[]` on any failure **and** left the settled promise parked in its
    `inflight` memo while `cache` stayed empty, so the memo was never replaced — one transient
    failure pinned the 평론 facet empty, silently, for the life of the page.
  - `hasMore` / `loadMore` had always been on the hook and `/search` wired neither, so every bucket
    stopped at 20 rows with no way to tell a complete answer from a first page.
  - every query commit used `replaceState`, which destroys the entry you came from: after searching
    `miles` and typing `davis`, Back left `/search` entirely. History now pushes on the first edit
    after an *arrival* (a link, a submit, or a back/forward landing) and replaces for the rest of
    that burst, so a typing burst still costs one entry.
  The filter pills also dropped `role="tab"`/`role="tablist"` for `aria-pressed` toggles — 전체 shows
  four sections at once, so there was never a tab ↔ tabpanel relationship for that role to describe,
  and the markup had no `tabpanel`, no `aria-controls` and no roving focus to back the promise. The
  result summary became a live region, mounted before it has anything to announce.
- **Leg 4 — the seams between finished features** (front #438 `03f19ae`, deploy `33570601690`,
  prod smoke 19/0, 2026-09-02). The Release Radar could only ever be filled from inside
  `/releases` (preview a bucket, or import Spotify follows), so the artist hub — where a reader
  decides an artist matters — got a track toggle on the existing `tracked-artists` contract.
  `/collection` named each shelf's owner in plain text under a comment reading *"no /members link
  until member pages are runtime-reachable"*; that had stopped being true without the comment
  noticing, and `/members/?u=<handle>` was already linked from the members hub and every rating
  byline, so this was the one surface that named a member and dead-ended on them. An accepted Spotify
  sync said `동기화 요청됨` and stopped, leaving the reader holding rows they cannot add; all four
  search surfaces now offer the catalog re-read. Verified on production after deploy: the collection
  attribution renders as a link and lands on a populated member page (`/members/?u=user-0468fd3c`,
  37 ratings), and the track control renders and is styled on a cold open of a real artist page by a
  signed-out visitor — so the feature is *findable*, not merely functional.

### What the browser found that the tests could not

Three defects in this work were caught by using it, not by reading or running the suite — worth
recording because two of them were green under a full gate at the moment they were wrong.

- **The retry cancelled itself** (leg 3, caught before merge). `retryAll()` called `runDbSearch()`
  *and* bumped the tick whose effect calls the search core's `setQuery`, which invalidates the search
  sequence and aborts whatever is in flight — including the request the retry had started a moment
  earlier. Retry "succeeded" into an empty page. A mocked hook made
  `expect(runDbSearch).toHaveBeenCalled()` pass throughout; the replacement test drives the **real**
  core and asserts results rather than a call.
- **`더 보기` was one-shot** (found by clicking leg 3's new button against production; fixed in leg
  4). `loadMore` set a `didAppend` flag *inside* the `setBuckets` updater and read it on the next
  line. React runs an updater during render, not at the call site, and the one case where it
  evaluates one eagerly requires the fiber to have no pending lanes — which `setLoadingMore(kind)` a
  few lines earlier guarantees it does not. So the flag was always `false`, every successful page
  took the "the API repeated itself" branch, `lastReturned` was zeroed (hiding the button) and the
  function returned before `offsets` advanced. Pre-existing, and unreachable until leg 3 wired the
  button up.
- **`/artist/[id]` called a failed load a missing artist** (found while opening the page for leg 4's
  track toggle). `getHero` has always reported *why* it failed — `404`, an HTTP status, or `0` for a
  transport error — and `ArtistHub` collapsed all three. This is exactly leg 3's defect class, and
  **leg 3's own audit missed it**: that sweep grepped for error-swallowing `catch` blocks and checked
  `/releases`, `/radar` and `/genres`, and this surface throws the distinction away at the call site
  instead, with no `catch` to find.

A fourth correction came from mutation-testing rather than the browser. The first draft of leg 3
claimed the result summary had been *recreated inside a branch* at the moment it had something to
announce; the mutant restoring that shape **survived**, because React reuses the node across a
symmetric ternary. The real defect was simpler — the summary carried no live-region semantics at all
— and the comment and the test were rewritten to the fact rather than left plausible-sounding.

### Deliberately not done

- **Durable job-status for sync/import completion.** Leg 4's `syncRequested` offers a catalog
  re-read; it does not claim the worker finished, because there is no contract to ask. Moved to
  Backlog as `FEAT-durable-job-status` rather than smuggled into a UI batch.
- **`ReleaseRadar` keeps its own `tracked-artists` call sites.** Its flows (bulk preview, Spotify
  import, the feed load it shares a `Promise.all` with) are not the new module's call shape, and it
  has no test coverage to refactor against.
- **AlbumOverlay action parity** remains under the existing album-card decision; **dynamic artist
  404/noindex** remains the previously accepted hosting trade-off; **overlay Back behaviour** still
  wants a real-browser product check before anyone changes it. None of the three is a defect this
  audit found — they are pointers to decisions that already live elsewhere.

## FIX-auth-identity-lifecycle — one account boundary for async auth and private client state (2026-08-30 → 2026-09-02)

→ `docs/archive/done/rfcs/FIX-auth-identity-lifecycle.md`. Accepted and closed the same day the last
step shipped; three serial steps, all front-only, no server contract, migration or Cognito
configuration change. The problem was that an authenticated browser identity was not a boundary:
a delayed Cognito refresh could restore tokens *after* logout and was not bounded by `apiFetch`'s
timeout, persistent Pocket and playback singletons were not account-scoped, and a login handoff
resumed a URL rather than the action the visitor had started.

- **Step 1 — auth generation and account-scoped private reset** (front #439, `e8eb156`, deploy
  `33574285362`, prod smoke 19/0). `src/lib/authIdentity.ts` publishes identity plus a monotonic
  generation and an `AuthEpoch` that gates every token commit, in-tab and across tabs. `apiFetch`'s
  deadline now covers the 401 refresh, so a slow network can no longer sign a user out; `bucketStore`
  rescopes and drops account A's in-flight read; the Pocket provider closes private UI and
  account-scopes `pb:drawers:<sub>`; playback ownership stamps and filters bus envelopes by account
  and releases the lease at the boundary. 60 named cross-tab regression tests (982 total, 0 skipped),
  16 mutants applied and 15 killed.
- **Step 2 — general post-login intent** (front #440, `3685350`, deploy `33577690006`, prod smoke
  19/0). The predecessor was a Pocket-only blob drained by a *home-mounted* consumer while the
  callback returned to the source route, so a logged-out 담기 on a review or album page was silently
  lost — a live production defect, not just fragmentation. `src/lib/postLoginIntent.ts` is one tagged
  TTL-bounded store and `components/auth/PostLoginResume`, mounted in `layout.astro`, is its single
  consumer. Rating parks an intent at all for the first time; its CTA used to send the visitor to
  Cognito with nothing saved. TTL, tag and the account boundary all drop rather than replay.
- **Step 3 — browser validation and residual cleanup** (front #441, `4280155`, deploy `33614309445`,
  prod smoke 30/0). Every invariant re-tested against the deployed bundle as a real signed-in
  account, each with a control that shows the assertion could have failed.

### What the browser found that the tests could not

**Step 3's clickthrough found a defect that Step 2's own fix had created** — the second RFC running
where a fully green suite shipped a broken boundary. `PostLoginResume` is layout-mounted, which is
what makes the resume land wherever the callback does; it also means *every open tab* is a consumer,
re-attempting its drain on every account change, while the intent lives in `localStorage`, which all
tabs share. Signing in was a race the visitor's own tab lost. With tab count as the only variable, on
`/search?q=radiohead`:

| other tabs open | the tab that signed in | the other tab |
|---|---|---|
| 0 | «Radiohead» 담기 picker | — |
| 1 (sitting on `/canon/`) | nothing at all | «Radiohead» 담기 picker |

A probe injected before any page script showed the key already gone at the landing document's start,
consumed ~250 ms earlier while `/admin/callback` was still running. The fix gives a record an owning
tab in `sessionStorage` — per-tab, and confirmed to survive the hosted-UI round trip on the deployed
bundle rather than assumed. **The tab id is a delivery address, not a permission**: the account gate
still runs after it, and is what keeps A's parked add out of B's bucket. Re-running the experiment
against the deployed fix in a fresh profile inverts the second row and leaves the first unchanged.

A mutation survivor corrected the explanation rather than the test: "the picker opens" passes even
when the write path records *nothing*, because an unowned record is claimable by anyone.

### The production-observability constraint was false

Step 2 recorded that the resume half could not be verified under a genuine session, because a real
Cognito login would have put the smoke password through the session transcript. Step 3 removed that
constraint rather than working around it: **drive Chrome over CDP from a local Node script instead of
through a tool call**, and the password and minted tokens are read from disk by the driver and typed
into the hosted UI directly, never passing through a transcript. Cross-document state is read with a
`Page.addScriptToEvaluateOnNewDocument` probe, and async boundaries are exercised by holding the real
response at the `Fetch` **Response** stage and releasing it with `continueResponse` — a synthetic 200
injected at the Request stage makes the control pass too, which proves nothing. Recipe recorded in
memory as `reference-authed-front-prod-cdp-e2e`.

### Not verifiable in production

The playback **lease** release could not be exercised: `GET /api/playback/spotify-token` answers 404
for an account with no connected Spotify integration, which is the route's designed dormant response,
so the transport never initialises and `ensureOwner()` is never reached. Not a defect. That half of
the account boundary rests on Step 1's tests plus Step 3's bus-filter result, and becomes observable
the first time a test account connects Spotify.

### Deliberately not done

- **Re-keying the playback lease per account.** Step 1 decided against it explicitly; it would be a
  new decision, not leftover homework.
- **The four `pb:resume` mentions still in `src`.** A one-deploy legacy migration read plus the
  comments explaining the change. Cleanup past the migration window is an owner call.
- **Spotify candidate/sync as a post-login intent.** May join only when its explicit public UI
  exists.
- Both open questions closed at their stated defaults (owner, 2026-09-02): drawer layout is
  account-private, because bucket ids and open positions reveal private tree structure; logout
  releases and resets this site's playback controller and issues **no** remote pause.
