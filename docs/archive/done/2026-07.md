## Feature expansion

### FEAT-lyrics-corpus: private, correctness-first lyrics corpus — ✅ 2026-07-02 (all steps prod-verified)

A **private, single-owner, correctness-first** lyrics corpus attached to catalog tracks. LRCLIB = only lyric-text source (plain + synced); MusicBrainz = identity/version evidence only; lyrics.ovh excluded. Lyrics are **owner-only** — never in any public API/page/search/shared/edge-cached response (mirrors `artists.aliases` / `album_research`). Album name is never a hard match key; the conservative matcher (`decide_match`) parks remix/live/demo/edit/cover/remaster/rerecording as `ambiguous`/`review_required` rather than mis-merging. RFC → `docs/rfcs/FEAT-lyrics-corpus.md` (Status: **done**).

- **Step 0** docs; **Step 1** shared_db `track_lyrics` store + match-status lifecycle + `Track.isrc` (V33/V34, 20.7k tracks); **Step 1b** worker ISRC backfill (myblog_worker #54).
- **Step 2** offline matcher (#478): Phase 1 (N=100 API sample, precision 39/39). Phase 2 matched the **full 20,946-track catalog** via LRCLIB `/api/search` (the 30.68 GiB dump wouldn't fit ~54 GiB disk) — matched 7,955 (38.0%) / no_lyrics 417 / not_found 9,798 / ambiguous 2,743 / review_required 33; consistency PASS, version-conflict false-match 0, precision 64/64 = 100% audited. 91% of matched carry synced (LRC).
- **Step 3** worker incremental collection (worker #57 + ws #481) — `lyrics_incremental` EventBridge job `rate(12 hours)`, alias-fill pattern: recently-added tracks lacking a row → LRCLIB `/api/search` → same matcher → per-row commit + sentinel; transient-skip isolation; bounded to the 120s Lambda. Prod-verified via a seeded 1-track gap.
- **Step 4** periodic reassessment + replacement guard (worker #58 + ws #483) — `lyrics_reassessment` job `rate(1 day)`: re-checks the unresolved pool (~12.5k, stalest-first) → promote-or-refresh; **replacement guard** never downgrades/laterally-swaps a good match (basis ladder isrc>mb-recording>exact-title>fuzzy-title → matched never replaced by the current matcher). Shared eval loop (`lyrics_eval_core.run_eval_batch`) used by Steps 3 & 4. Prod-verified: 30/30 unresolved refreshed, 0 promotions (same-day), 0 matched touched.
- **Infra**: `terraform apply`-ed `worker-lyrics-incremental` + `worker-lyrics-reassessment` EventBridge rules. **No frontend, no public API.** Consumers (viewer/translation/interpretation) are separate later RFCs — see FEAT-lyrics-viewer.

### FEAT-pocket-buckit-viewers: bidirectional DnD + per-drawer Card Viewer — ✅ 2026-07-01

Two front-only, additive extensions to Pocket Buckit, both over the shared `bucketStore` (one source of truth → every island repaints off one optimistic update, so "reflected immediately everywhere" is free). 2 tracks, sequential (Hard rule #4). **No new bucket types, membership rules, API, contract, schema, or infra.**

- **Track A — reverse DnD (front #218, ws #470, 2026-06-30).** The *reverse* of FEAT-my-buckit-artist Step 6: a board My Buckit member dragged onto a Pocket target (tray chip / open drawer) is added to that bucket with the **board's exact semantics**. A symmetric cross-island bridge (`PB_BOARD_DND_START`/`END` board→pocket, `PB_BOARD_DROP` pocket→board) carries the live drag; the board's inline bucket-drop routing was extracted to a board-scope `dropOnBucket(targetBucketId)` that **both** the card `onDrop` and the `PB_BOARD_DROP` listener call (no duplicated routing → General/Artist + artist-expansion semantics provably identical). The Pocket island mirrors the board drag in a `boardDnd` module so chips/drawers preview droppability via a 3-line replica of `canAcceptAlbumDrag`. Existing Pocket→board (Step 6) wiring untouched. **Verified** headless CDP (real Chrome synthetic DragEvents + mock backend, console 0): General drop = cross-bucket **move** (`PUT /reorder` via `ops.insertAlbum`), Artist drop = **source-expansion** (`POST source_album_id`), accept-gate `data-droppable`/`data-drophot` correct, Step 6 intact; prod bundle carries `pb:board-drop`/`pb:board-dnd-start`/`data-drophot` (deploy 28442412334).

- **Track B — per-drawer Card Viewer (front #219, 2026-07-01).** The bucket window opened from a tray chip gains an **ephemeral per-open-drawer** Current ⇄ Card viewer toggle (header button). Card Viewer renders the same `bucket.albums` as a **board-style square-cover grid** — album = cover, artist = square photo + `아티스트` badge, artist tile click → `/artist/[id]` (mirrors the board); album/other tiles are non-navigating (no in-island detail surface). Reads the same provider bucket as the list, so a change via the board, reverse DnD, or edit `−` reflects live in every viewer; two drawers toggle independently. `Cover` gained optional `url`/`square` to show the real cover via the **site-wide global** `.cover`/`.cover img` (no `member.css` dependency); list rows + card tiles share a `dragBind` so the Step 6 drag-out and edit-`−` work in both modes. Tile/grid/toggle styles are self-supplied in `pocket.css` (`.pb-cardgrid` / `.pb-card*` / `.pb-viewtoggle`) because `member.css` (the board's `.bb-tile`/`.lf-cover`) is `/profile`-only and the site-wide drawer must not depend on it. Open-Q 1 resolved: render **all** members in the existing scroll area (no slice cap). **Verified** headless CDP **off-`/profile`** (homepage + mock backend): list⇄card toggle, 2 `<img>` covers + 1 placeholder render with `member.css` NOT linked & `.bb-tile` rule absent (proves self-supply), artist tiles + badge + click→`/artist/ar1`, two drawers with independent per-window mode, edit-`−` live reflection (card grid 3→2 + tray chip badge 3→2); console clean. Prod bundle `PocketBuckit.BqMp8rYZ.js` + CSS `Cc5GMNRB.css` carry all Track B markers (deploy 28479488342).

**Caveat (both tracks):** a *trusted native HTML5 drag gesture* can't be synthesized headlessly (same as Step 6 / Track A) — the drag routing is exercised via synthetic events + the verbatim reused payload; the real gesture is an owner spot-check on prod.
