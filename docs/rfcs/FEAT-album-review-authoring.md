# FEAT-album-review-authoring: 앨범 리뷰 쓰기 경험 (통합 입구 · AI 정리 도움 · 프로필 평점 이력)

- **Status**: draft
- **Owner**: TBD (오너 accept 필요)
- **Created**: 2026-07-30
- **Plan row**: `plan.md` → FEAT-album-review-authoring
- **선행 RFC**: `FEAT-multi-user-accounts` (Phase 1에서 앨범 평점·리뷰의 뼈대가 이미 출시됨 — 이 RFC는 그 위에 얹는 증분)

> 이 문서는 제품 정의 문서다. 구현 방법·구조·데이터 모델·API·마이그레이션·테스트·검증 절차는 **의도적으로 쓰지 않는다**. 그것들은 오너가 이 문서를 accept한 뒤 별도로 정한다.

---

## Goal

사용자가 앨범에 대한 자기 감상을 **막힘 없이 남기고, 자기 평점 이력을 한눈에 되돌아볼 수 있게** 한다. 구체적으로 세 가지가 참이 된다. (1) 제품 어디에서든 "쓰기"라는 하나의 입구로 들어가고, 그 입구가 사용자의 권한에 맞는 것만 보여준다 — 일반 사용자는 **리뷰**, 편집 권한 사용자는 **평론과 리뷰 중 선택**. (2) 사용자는 짧은 리뷰를 바로 쓸 수도 있고, 정리되지 않은 자유 감상을 적어 **AI에게 짧은 리뷰로 정리해 달라고 요청**할 수도 있다. AI 결과는 편집 가능하고, **발행은 반드시 사용자가 명시적으로 누른다**. 자유 감상 원문은 **작성자만 볼 수 있게 남는다**. (3) 프로필에서 자기(그리고 남의) **평가한 앨범 수 · 평균 평점 · 평점 분포 · 앨범 리뷰 목록**을 보고 정렬·탐색할 수 있다.

이미 출시된 것(0.5단위 평점, 선택 코멘트, 1인 1앨범, 수정·삭제, 앨범 평균·개수, 프로필의 최신순 목록)은 **이 RFC의 작업이 아니다.** 아래 "이미 있는 것" 표가 경계선이다.

## 용어 결정 (이 RFC의 첫 번째 산출물)

제품에 두 종류의 글이 있고, 지금 문서와 UI가 이 둘을 같은 단어로 부르고 있다. 이 RFC는 용어를 다음으로 **고정**한다.

| 용어 | 뜻 | 쓰는 사람 | 발행 성격 |
|---|---|---|---|
| **평론** | 긴 편집 콘텐츠(장문 비평) | 편집 권한을 가진 사용자 | 정식 발행물. 사이트의 편집 지면에 실린다 |
| **리뷰** | 앨범 하나에 대한 **공개 평점 + 짧은 개인 감상** | 로그인한 모든 사용자 | 즉시 공개되는 개인 기록. 편집 지면이 아니다 |

- 두 글은 **하나의 쓰기 입구**를 공유할 수 있으나, 권한·기대치·발행 동작은 계속 분리된다.
- **평점만 남기는 것도 리뷰다** (글 없이 평점만 = 리뷰의 정상 상태). 개수·평균·분포·목록에 모두 포함된다.
- 리뷰는 **앨범 단위만** 존재한다. 트랙·아티스트 리뷰는 이 RFC의 범위가 아니다.

용어 정리의 실행 범위는 **화면에 보이는 문구까지**로 한정한다. URL(`/review/…`, `/reviews/`), API 경로, 테이블·타입 이름 같은 내부 식별자는 바꾸지 않는다 — 바꿔서 얻는 이득이 SEO·계약 변경 비용보다 작다. (남는 불일치는 아래 "문서·UI 충돌" 표에 기록해 둔다.)

## Non-goals

- 트랙 리뷰, 아티스트 리뷰
- AI 결과의 자동 발행 (어떤 조건에서도 없음)
- 장르·아티스트 통계, 차트
- 댓글·좋아요·팔로우 등 소셜 기능
- 편집용 리서치 노트 파이프라인 변경 (`album_research` 계열은 손대지 않는다)
- 추천·발견(디스커버리) 기능 확장
- 평론(장문 편집물)의 작성 경험 개선 — 이 RFC는 **입구에서 평론을 고르게 하는 것**까지만 다루고, 평론 편집기 자체는 건드리지 않는다
- 다중 저자 편집(평론 권한을 오너 밖으로 넓히는 일) — `FEAT-multi-user-accounts`의 cold 항목으로 남는다
- 조절(모더레이션) 체계 확장 — 기존 최소 장치(일일 생성 상한 + 오너 삭제)를 그대로 쓴다

## Current state (2026-07-30 코드 확인)

**이미 있는 것 — 이 RFC가 새 작업으로 세지 않는 것**

| 사용자에게 보이는 동작 | 현재 상태 |
|---|---|
| 앨범 상세(공개 오버레이 + 회원 모달)에서 0.5단위 별점 입력 | 있음 (`AlbumRatingBlock`, `AlbumDetailView.topSlot`) |
| 별점과 함께 짧은 글 남기기 (선택) | 있음 — 입력칸 안내 문구가 "한 줄 감상 (선택)" |
| 1인 1앨범 1리뷰, 다시 쓰면 수정 | 있음 |
| 내 리뷰 삭제 / 오너의 임의 리뷰 삭제 | 있음 |
| 앨범 화면의 커뮤니티 평균 + 평가 개수 | 있음 (읽기 시점 계산, 별도 집계 컬럼 없음) |
| 홈 앨범 카드 · Buckit 앨범 카드 · 검색 결과에서 카드를 누르면 그 앨범의 평점 패널까지 도달 | 있음 (카드 → 앨범 오버레이 공통 진입) |
| 공개 프로필의 "평가한 앨범" 최신순 목록 (표지·제목·별점·날짜·코멘트) | 있음 (`MemberProfile`) |
| 프로필 상단 "N개 평가" 카운트 | 있음 |
| 자기 프로필에서만 보이는 대시보드 탭(개요/평론/My Buckit/분석 버킷/연동) | 있음 |
| 일일 리뷰 생성 상한(초과 시 안내) | 있음 |

**없는 것 — 이 RFC가 정의하는 것**

- **일반 사용자에게는 쓰기 입구가 아예 없다.** 헤더의 "글쓰기"는 오너 신호로 숨겨져 있어(`isOwnerUser`) 일반 회원은 어떤 쓰기 진입점도 보지 못한다. 리뷰를 남기려면 앨범 화면까지 스스로 찾아가야 한다.
- **쓰기 종류를 고르는 개념이 없다.** 평론/리뷰를 같은 자리에서 고르는 화면이 존재하지 않는다.
- **자유 감상 → AI 정리 경로가 없다.** 사용자 글에 AI가 개입하는 지점이 제품에 하나도 없다. (편집용 리서치 노트 파이프라인은 오너 전용이고 사용자 글과 무관하다.)
- **비공개로 남는 사용자 텍스트가 없다.** 현재 사용자 글은 전부 공개다.
- **자기 평점의 평균·분포가 어디에도 안 보인다.** 앨범별 평균은 있으나 사용자별 평균은 없다. 목록 정렬·필터도 없다. (예전에 만들어 둔 통계 계산 함수 `computeStats`는 **아무도 호출하지 않는 죽은 코드**다 — "이미 있다"고 오해하기 쉬운 지점.)

**주변 사실 (경계를 정할 때 필요한 것)**

- 회원 프로필 페이지는 **빌드 시점에 미리 만들어진다.** 새 회원의 프로필 주소는 다음 배포 후에 생긴다. 앨범 화면의 평점 쓰기·읽기는 즉시 동작한다. (`FEAT-multi-user-accounts`에 남아 있는 "런타임 프로필 vs 정적 프로필" 결정이 아직 열려 있다.)
- 평론의 발행 경로와 리뷰의 저장 경로는 **원래부터 다르다.** 평론은 정적 발행물로 나가고, 리뷰는 서비스 데이터로만 존재한다. 이 분리는 유지한다.
- 사용자 요청으로 모델을 호출하는 통로는 **아직 아무 곳에서도 쓰이지 않는다.** 공용 LLM 계층과 사용량 계량 자리는 `FEAT-multi-user-accounts` Phase 4에서 뼈대만 들어와 있고, 실제 호출자는 0이다. 즉 **이 RFC의 AI 도움 기능이 제품 최초의 사용자 요청 기반 AI 호출**이 된다.
- `/write` 화면 자체는 로그인만 확인한다(오너 확인 없음) — 2026-07-26 감사 E-5. 헤더에서 숨겨져 있어 지금은 눈에 띄지 않지만, **일반 사용자에게 쓰기 입구를 여는 순간 이 구멍이 실제 사용자 경로가 된다.**

## Target state — 사용자에게 보이는 능력 단위

각 항목은 "사용자가 무엇을 할 수 있게 되는가"로만 쓴다. 배치·문구·수치는 정하지 않은 것은 정하지 않은 상태로 둔다(→ Open questions).

### C1. 하나의 쓰기 입구

- 제품 전체에서 쓰기 진입은 **일관된 하나의 입구**로 느껴진다. 진입 지점은 (a) 전역 헤더, (b) 앨범 정보 화면, (c) 홈의 앨범 카드, (d) Buckit 안의 앨범 카드다.
- **앨범 카드나 앨범 화면에서 들어오면 그 앨범이 이미 선택된 상태**로 시작한다. 사용자가 앨범을 다시 찾을 필요가 없다.
- **헤더에서 들어오면 사용자가 종류와 앨범을 고른다.**
- 권한:
  - 일반 사용자 → 리뷰를 쓸 수 있다.
  - 편집 권한 사용자 → **평론과 리뷰 중 고른다.**
  - 편집 권한이 없는 사용자에게 **쓸 수 없는 평론 항목을 보여주지 않는다.** (누르면 막히는 항목을 노출하지 않는다.)
- 입구를 공유하더라도 **두 글의 성격 차이가 흐려지면 안 된다.** 사용자가 "지금 내가 쓰는 게 공개 개인 평가인지, 편집 지면에 실리는 비평인지" 혼동하지 않는 상태가 이 능력의 합격선이다.

### C2. 리뷰 쓰기 — 유지되는 것과 달라지는 것

- **유지**: 평점 규칙, 글 없이 평점만 남기기, 1인 1앨범 1리뷰, 수정, 삭제, 앨범 평균, 평가 개수. 이 RFC는 이 규칙들을 바꾸지 않는다.
- **달라지는 것**: 짧은 리뷰를 **직접 쓰는 길**과 **자유 감상을 AI에게 정리받는 길**이 같은 흐름 안에서 나란히 제시된다. 직접 쓰는 사용자는 AI를 전혀 만나지 않고 지금과 같은 경험으로 끝낼 수 있어야 한다.
- 발행된 평점과 리뷰는 **공개**다.

### C3. 자유 감상 → AI 정리 (선택)

- 사용자는 정리되지 않은 긴 감상을 자유롭게 적을 수 있다.
- 원하면 **AI에게 짧은 리뷰로 정리해 달라고 요청**한다. 요청하지 않으면 아무 일도 일어나지 않는다.
- AI는 **제품이 제공하는 기본 프롬프트**로 동작한다. 사용자가 프롬프트를 쓰지 않는다.
- **AI 결과는 사용자가 편집할 수 있다.**
- **발행은 사용자가 명시적으로 한다. AI 산출물이 저절로 공개되는 경로는 없다** — 이 문장은 이 RFC의 하드 규칙이다.
- **개방 순서 (오너 결정 2026-07-30)**: AI 도움은 **오너 계정에서 먼저만 보인다.** 오너가 실제 결과 품질과 비용을 확인한 뒤 일반 사용자에게 연다. 그전까지 일반 사용자에게는 AI 항목이 노출되지 않고, 직접 쓰는 길만 보인다 — C1의 "쓸 수 없는 것을 보여주지 않는다"와 같은 원칙이다. 이 시범 게이트는 **편집 권한과 별개의 축**이다(평론 권한이 아니라 "AI 도움이 아직 시범 중"이라는 이유로 가려진다).
- 길이 기준(한 줄인지 문단인지, 글자 수 상한)은 **아직 정하지 않았다** (→ OQ1).

### C4. 자유 감상 원문의 비공개 보관

- 사용자가 적은 **원문은 작성자 본인에게만 보인다.** 다른 사용자·비로그인 방문자에게 어떤 형태로도 노출되지 않는다.
- 원문은 발행 이후에도 남는다 (다시 정리하거나 스스로 되돌아보기 위한 것).
- **연결된 리뷰를 삭제하면 보관된 원문도 함께 삭제된다.** 리뷰 없이 원문만 남는 상태는 만들지 않는다.
- 원문은 제품의 **첫 비공개 사용자 데이터**다. 선행 RFC의 "모든 것은 공개, 공개 범위 설정은 없다"는 결정과 정면으로 만나므로 아래 "문서·UI 충돌"에서 명시적으로 정정한다.

### C5. 프로필의 평점 이력

프로필에서 자기 앨범 평가 이력을 **되짚고 이해할 수 있게** 한다. 보이는 것:

- 평가하거나 리뷰한 **앨범 수**
- **평균 평점**
- **평점 분포**
- **앨범 리뷰 목록**
- 목록을 훑고, 정렬하고, 개별 리뷰를 열어 보기

**평점만 남긴 항목도 앨범 수·평균·분포·목록에 모두 포함된다.** (글 있는 것만 세는 화면은 만들지 않는다.)

이미 있는 프로필 능력(최신순 목록, 표지·별점·코멘트 표시, 앨범 열기, 개수 카운트)은 **재사용한다.** 새 범위는 **평균 · 분포 · 정렬/탐색**이며, 기존 목록을 대체하는 것이 아니라 그 위에 덧붙는다.

## 경계와 규칙

1. **평론은 편집 권한 사용자만.** 이 RFC는 편집 권한을 넓히지 않는다.
2. **AI 산출물의 자동 발행 금지.** 예외 없음.
3. **비공개는 원문 한 곳뿐.** 리뷰·평점·프로필 통계는 전부 공개다. 원문 보관을 이유로 일반적인 공개 범위 설정 기능을 도입하지 않는다.
4. **리뷰는 앨범 단위.** 트랙/아티스트로 확장하지 않는다.
5. **편집 지면과 개인 기록의 구분 유지.** 리뷰가 편집 지면(평론 목록·평론 상세)에 섞여 들어가지 않는다.
6. **기존 리뷰 데이터는 그대로 유효하다.** 이미 남아 있는 평점·코멘트가 새 흐름 때문에 다시 쓰이거나 성격이 바뀌는 일은 없다.

## Dependencies (이 기능이 기대고 있는 것)

- **사용자 요청 AI 호출 통로** — 공용 LLM 계층은 뼈대만 있고 호출자가 없다. C3은 이 통로의 첫 사용자다. 따라 붙는 제품 질문은 **비용과 응답 지연을 사용자에게 어떻게 보이게 할지**이며(→ OQ4), 오너의 비용 성향($0 편향)이 강한 제약이다.
- **`/write` 권한 구멍 (감사 E-5)** — 일반 사용자에게 쓰기 입구를 여는 것과 같은 범위에서 정리되어야 한다. C1의 "쓸 수 없는 항목을 보여주지 않는다"는 이것이 정리되지 않으면 성립하지 않는다.
- **회원 프로필 페이지의 생성 방식** — 프로필이 배포 시점에 만들어지는 현재 방식에서는 신규 사용자가 자기 통계 화면을 즉시 갖지 못한다. 선행 RFC에 열려 있는 프로필 주소 결정과 직접 얽힌다(→ OQ5).
- **선행 RFC의 공개 게이트(G1)** — "실사용자 리뷰가 쌓이는가"를 재는 게이트가 아직 열려 있고, 오너가 공개 시점을 무기한 미뤄 둔 상태다. 이 RFC는 **그 게이트를 통과하기 쉽게 만드는 쪽의 작업**이지, 게이트를 대체하지 않는다.
- **손대지 않는 것** — 음악 카탈로그 수집 계열(`DATA-*`), 가사·주석 계열(`FEAT-lyrics-annotations`), 편집 리서치 노트(`CHORE-research-prompt-port-not-swap`)와 겹치는 범위가 없다. 이 RFC는 그쪽 일정과 독립적으로 진행·중단할 수 있다.

## 우선순위 안에서의 위치

- 오너의 2026-07-23 결정(안전망·품질 우선, 디스커버리는 뒤)은 유지된다. 이 RFC는 디스커버리가 아니라 **이미 있는 핵심 흐름(듣기 → 담기 → 남기기)의 마지막 한 칸**을 채우는 작업이고, 지금 제품에서 일반 사용자가 쓰기를 시작할 통로가 아예 없다는 점에서 **가장 작은 사용자 향 개선**에 해당한다.
- 선행 RFC에 남은 것은 전부 오너 액션(공개 심사·게이트 관측)이고, 이 RFC는 그것과 병렬로 진행 가능하다.
- 리뷰 볼륨에 걸려 얼어 있는 항목들(`FEAT-genre-recommendation`, `FEAT-ai-editorial-critique`)보다 **앞**이다. 그 항목들의 전제 조건이 "리뷰가 쌓인다"인데, 이 RFC가 그 전제를 만드는 쪽이다.
- **범위는 쪼개지 않는다 (오너 결정 2026-07-30).** C1·C3·C4·C5를 하나의 기능으로 본다. 초안의 권고는 "C1+C5 먼저, AI 뒤"였고 오너가 전체 한 묶음을 택했다.
  - 이 선택이 감당하는 것: AI 도움은 **비용 · 기본 프롬프트 품질 · 제품 최초의 비공개 사용자 데이터** 세 가지를 동시에 들여온다. 이 부담은 "오너 먼저 시범" 게이트(C3)로 낮춘다 — 일반 사용자에게 열기 전에 오너가 결과를 직접 보게 되므로, 품질이 나쁘면 **연다는 결정을 안 하는 것으로** 되돌릴 수 있다. 즉 되돌리기 지점이 코드가 아니라 개방 판단에 있다.
  - 남는 전제 위험: 지금 오너 외에 리뷰를 남긴 사용자가 **0명**이고 공개 게이트 G1은 오너가 무기한 미뤄 둔 상태다. 따라서 C1(입구)의 효과는 **공개 이후에만 측정된다.** 반면 C5(프로필 평점 이력)와 C3의 오너 시범은 사용자 수와 무관하게 오늘 값이 나온다 — 한 묶음으로 가더라도 **먼저 값이 확인되는 조각은 이 둘**이라는 사실은 유지된다.

## Open questions

각 항목은 무엇이 막히는지 함께 적는다. 정해지지 않은 것을 정해진 것처럼 쓰지 않는다.

1. **리뷰 글의 길이 기준** — 한 줄 고정인가, 짧은 문단인가, 아니면 사용자가 고르는가? 상한 글자 수는? 지금 화면은 "한 줄 감상"이라 안내하면서 실제 상한은 그보다 훨씬 크다(안내와 실제가 다름). *막는 것*: C2·C3의 결과물 형태와 AI 기본 프롬프트의 목표 길이. *대안*: (a) 한 줄 고정 — 훑기 쉽고 AI 정리의 목표가 명확해진다, (b) 짧은 문단 허용 — 표현 여지가 크다, (c) 지금처럼 열어 두고 안내 문구만 정직하게 고친다(가장 작은 변화).
2. **"평가"와 "리뷰"를 사용자에게 어떻게 부를지** — 평점만 남긴 항목까지 포함하는 이름이 필요하다. *막는 것*: 충돌 #3의 문구 정리, C5의 화면 이름. *대안*: (a) 전부 "리뷰"로 부르고 글 없는 것도 리뷰로 센다, (b) "평점"과 "리뷰"를 나눠 부르고 통계에는 둘 다 포함한다 — 정확하지만 화면에 단어가 둘로 늘어난다.
3. **AI 정리가 무엇을 하는 도움인지** — 요약인가, 다듬기인가, 관점 뽑아내기인가? 기본 프롬프트의 성격이 결과물의 성격을 결정한다. 여기서 문구를 임의로 정하지 않는다. *막는 것*: C3 전체. *주의*: 편집용 리서치 노트 프롬프트와 목적이 전혀 다르므로 재사용 대상이 아니다.
4. **AI 도움의 비용·지연을 사용자에게 어떻게 보이게 할지** — **개방 순서는 결정됐다**(오너 2026-07-30: 오너 시범 → 일반 개방). 남은 것: 일반 개방 시 사용자당 사용 한도를 둘지, 기다리는 상태를 어떻게 보여줄지, 즉시 응답을 기대하게 할지. 오너의 $0 편향이 실질 제약이다. *막는 것*: 일반 개방 시점의 C3 사용자 기대치 — **오너 시범 단계는 막지 않는다.**
5. **신규 사용자의 프로필 통계 접근** — 프로필 페이지가 배포 시점에 생기는 현재 방식에서 갓 가입한 사용자는 자기 통계를 즉시 볼 수 없다. *막는 것*: C5가 "가입 직후 사용자"에게도 성립하는지. *대안*: (a) 선행 RFC의 프로필 주소 결정을 먼저 내린다, (b) 통계를 프로필 밖(자기 대시보드)에서 먼저 보여준다, (c) 실사용자가 생길 때까지 현행 유지.
6. ~~**범위 순서**~~ — **결정됨 (오너 2026-07-30): 전체 한 묶음.** 초안 권고(C1+C5 먼저)는 채택되지 않았다. 근거와 남는 위험은 위 "우선순위 안에서의 위치"에 기록했다.
7. **목록 정렬 기준** — 최신순 외에 무엇을 줄지(평점순, 앨범/아티스트 이름순 등). 임의로 정하지 않는다. *막는 것*: C5의 탐색 부분.
8. **더 단순한 대안 (기록용)** — "자유 감상 원문 보관"은 C3의 부수 효과로 생긴 저장물이다. 만약 원문을 남기지 않고 **AI 정리를 일회성 도움으로만** 두면(정리 결과만 남고 원문은 버림) 비공개 데이터·삭제 연동·프라이버시 예외가 전부 사라진다. 오너 요구는 "원문 보관"이므로 기본 방향은 보관이지만, C3 비용이나 프라이버시 부담이 커질 때 되돌아올 수 있는 더 단순한 선택지로 남겨 둔다.
9. **입구를 어디에 어떻게 놓을지** — 헤더 항목의 모양, 카드에서의 진입 방식, 종류 선택 화면의 형태는 정하지 않았다. 이 문서는 "일관된 하나의 입구"라는 성질만 규정한다.
